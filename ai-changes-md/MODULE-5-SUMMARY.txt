5. WHEN TO USE CLUSTER DEPLOYMENT
   
   Use Clusters When:
   - Data exceeds 1 TB capacity
   - Need high availability and fault tolerance
   - Multiple concurrent query users
   - Mission-critical analytics
   - Rolling updates required
   - High ingestion rates
   
   Single Node Sufficient When:
   - Development/testing environments
   - Data < 1 TB
   - Limited budget
   - Low query volume
   - Data loss acceptable

TROUBLESHOOTING GUIDE
================================================================================

If replication lag increases:
1. Check ZooKeeper connectivity
2. Verify network between replicas
3. Monitor merge operations
4. Check disk I/O on affected nodes
5. Review query load

If node becomes unavailable:
1. Data routes to other replica automatically
2. Check node health and logs
3. Restart node when ready
4. Replication catches up automatically
5. Monitor absolute_delay

If ZooKeeper quorum lost:
1. Check all ZK nodes are running
2. Verify network connectivity
3. Check disk space on ZK nodes
4. Review ZK configuration
5. Restart ZK ensemble

CUSTOMIZATION GUIDE
================================================================================

To change topology from 3×2 to 2×3:
1. Update <remote_servers> in config.xml
2. Define 2 shards with 3 replicas each
3. Update ZooKeeper settings if needed
4. Recreate tables with new topology

To add a 4th shard:
1. Add new shard definition in config.xml
2. Deploy ClickHouse on 2 new nodes
3. Restart cluster nodes
4. Rebalance data using ATTACH TABLE

To change replication factor:
1. Modify remote_servers configuration
2. Create new tables with new factor
3. Migrate data incrementally
4. Drop old tables

SUPPORT & TROUBLESHOOTING
================================================================================

If issues arise, refer to:
1. Official ClickHouse documentation (clickhouse.com/docs)
2. GitHub discussions (github.com/ClickHouse/ClickHouse/discussions)
3. Stack Overflow (search: [clickhouse])

Common Issues & Solutions:
- Replication lag: Check ZK health and network
- Query timeouts: Adjust max_execution_time
- OOM errors: Reduce max_memory_usage
- Slow inserts: Batch larger record sets
- High latency: Add more shards or optimize ORDER BY
