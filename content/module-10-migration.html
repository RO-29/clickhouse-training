📖 What is Migration to ClickHouse?

Migration Overview

Migrating to ClickHouse means transferring data from traditional OLTP databases (MongoDB, MySQL, PostgreSQL) to ClickHouse's column-oriented architecture for analytics. This is a critical operation that requires careful planning, schema transformation, data validation, and often involves running both systems in parallel during transition.

🗺️

Schema Mapping

Transform document/relational schemas into columnar format optimized for analytics

🔄

ETL Pipeline

Extract, transform, and load data with minimal downtime using streaming architecture

📡

Change Data Capture

Sync real-time changes using Debezium CDC and Kafka streaming

✅

Data Validation

Reconcile data integrity across source and target systems

Key Challenges in Migration

From MongoDB (Document DB)

  • Flattening nested/embedded documents
  • Handling schema variability (different documents have different fields)
  • Converting ObjectId to standard types
  • Handling arrays and complex types
  • Preserving TTL and expiration logic

From MySQL/PostgreSQL (Relational)

  • Denormalizing normalized schemas
  • Handling large volumes efficiently
  • Converting foreign key relationships
  • Managing ACID transaction semantics
  • Handling incremental updates and deletes

3. ClickHouse Kafka Engine consumes in real-time

Migration Phases

1. Assessment & Planning - Analyze data volume, schema complexity, dependencies
2. Schema Design - Design ClickHouse schema, define transformations
3. Setup CDC/Streaming - Configure Debezium, Kafka, ClickHouse Kafka Connect
4. Historical Data Migration - Bulk load existing data
5. Live Sync - Stream real-time changes from source
6. Validation & Testing - Compare data, run integration tests
7. Dual-Write Period - Run both systems in parallel
8. Cutover - Switch to ClickHouse, monitor for issues
9. Rollback Plan - Maintain ability to revert if needed
🚀 Quick Start: MongoDB to ClickHouse

Step 1: Analyze MongoDB Schema

// Sample MongoDB document
db.users.findOne()

{
  "_id": ObjectId("507f1f77bcf86cd799439011"),
  "name": "John Doe",
  "email": "john@example.com",
  "profile": {
    "age": 30,
    "country": "USA",
    "interests": ["tech", "sports"]
  },
  "created_at": ISODate("2024-01-15T10:00:00Z"),
  "updated_at": ISODate("2024-01-15T10:00:00Z"),
  "is_active": true
}

Step 2: Design ClickHouse Schema

-- Flattened, denormalized schema for ClickHouse
CREATE TABLE users (
    user_id String,        -- MongoDB ObjectId as String
    name String,
    email String,
    age UInt8,            -- From profile.age
    country String,       -- From profile.country
    interests Array(String), -- Flattened from profile.interests
    is_active UInt8,      -- Boolean as 0/1
    created_at DateTime,
    updated_at DateTime
) ENGINE = ReplacingMergeTree(updated_at)
ORDER BY user_id
PARTITION BY toYYYYMM(created_at);

Step 3: Install & Configure Debezium

#!/bin/bash
# Download Debezium Docker Compose
wget https://raw.githubusercontent.com/debezium/debezium-examples/main/docker-compose.yml

# Start Kafka + Debezium cluster
docker-compose up -d

# Create MongoDB connector
curl -X POST http://localhost:8083/connectors \
  -H "Content-Type: application/json" \
  -d '{
    "name": "mongo-connector",
    "config": {
      "connector.class": "io.debezium.connector.mongodb.MongoDbConnector",
      "mongodb.hosts": "mongo:27017",
      "mongodb.name": "my_source",
      "collection.include.list": "mydb.users",
      "publish.full.document.only": true,
      "output.format.value": "json"
    }
  }'

Step 4: Configure ClickHouse Kafka Table

-- Kafka table to receive streaming data
CREATE TABLE users_kafka (
    user_id String,
    name String,
    email String,
    age UInt8,
    country String,
    interests Array(String),
    is_active UInt8,
    created_at DateTime,
    updated_at DateTime
) ENGINE = Kafka()
SETTINGS
    kafka_broker_list = 'kafka:9092',
    kafka_topic_list = 'my_source.mydb.users',
    kafka_group_id = 'clickhouse_users',
    kafka_format = 'JSONEachRow';

Step 5: Create Materialized View to Sink Data

-- Materialized view that reads from Kafka and writes to MergeTree
CREATE MATERIALIZED VIEW users_mv TO users AS
SELECT
    user_id,
    name,
    email,
    age,
    country,
    interests,
    is_active,
    created_at,
    updated_at
FROM users_kafka;

Step 6: Bulk Load Historical Data

#!/bin/bash
# Export data from MongoDB
mongoexport --db=mydb --collection=users --out=users.json

# Transform and load to ClickHouse
cat users.json | clickhouse-client \
  --query="INSERT INTO users FORMAT JSONEachRow" \
  --input_format_json_try_infer_numbers_from_strings=1

Step 7: Validate Data

-- Count records in source
db.users.countDocuments()  // MongoDB: 1,000,000

-- Count records in ClickHouse
SELECT COUNT(*) FROM users;  -- ClickHouse: 1,000,000

-- Compare sample records
SELECT * FROM users LIMIT 5;

ClickHouse Kafka Setup

-- Create Kafka table for MongoDB changes
CREATE TABLE orders_kafka (
    _id String,
    order_id String,
    customer_id String,
    amount Float64,
    status String,
    created_at DateTime,
    updated_at DateTime,
    _op String,      -- INSERT, UPDATE, DELETE
    _ts UInt64       -- Timestamp
) ENGINE = Kafka()
SETTINGS
    kafka_broker_list = 'kafka1:9092,kafka2:9092,kafka3:9092',
    kafka_topic_list = 'mongo_source.myapp.orders',
    kafka_group_id = 'clickhouse_orders_group',
    kafka_format = 'JSONEachRow',
    kafka_num_consumers = 3,
    kafka_poll_timeout_ms = 3000,
    kafka_skip_broken_messages = 1;

-- Create target table
CREATE TABLE orders (
    order_id String,
    customer_id String,
    amount Float64,
    status String,
    created_at DateTime,
    updated_at DateTime
) ENGINE = ReplacingMergeTree(updated_at)
ORDER BY order_id
PARTITION BY toYYYYMM(created_at);

-- Materialized view to sink data
CREATE MATERIALIZED VIEW orders_mv TO orders AS
SELECT
    order_id,
    customer_id,
    amount,
    status,
    created_at,
    updated_at
FROM orders_kafka
WHERE _op IN ('c', 'u');

-- Find extra records (target -> source)

✨ Migration Best Practices

1. Schema Mapping Strategy

❌ Wrong
-- Trying to preserve MongoDB schema 1-to-1
CREATE TABLE user_docs (
    _id String,
    full_document String  -- Storing entire JSON
) ENGINE = MergeTree()
ORDER BY _id;

-- Problem: Queries require JSON parsing

Issue: Cannot efficiently query nested data

✅ Correct
-- Flatten and denormalize
CREATE TABLE users (
    user_id String,
    first_name String,
    last_name String,
    address_street String,
    address_city String,
    address_country String,
    phone_numbers Array(String),
    tags Array(String)
) ENGINE = MergeTree()
ORDER BY user_id;

-- Benefits: Fast queries, good compression

Advantage: Optimal for ClickHouse analytics

2. Historical Data vs Live CDC

Historical Data Migration

  • Use batch export tools (mongoexport, mysqldump)
  • Transform data offline before loading
  • Load in chunks to avoid memory issues
  • Verify data before marking as complete
  • Disable inserts during bulk load for speed

Live CDC Streaming

  • Start BEFORE historical migration
  • Capture all changes during migration window
  • Use Kafka for reliable streaming
  • Implement deduplication logic
  • Monitor lag and throughput

3. Data Validation Checklist

Validation Method Acceptable Threshold
Row count COUNT(*) comparison 100% match
Sample data MD5/SHA hash of sorted data 100% match
Aggregations SUM, AVG on numeric columns < 0.01% difference
Distinct values COUNT(DISTINCT col) 100% match
Date ranges MIN, MAX on date columns 100% match
NULL handling COUNT where col IS NULL 100% match

4. Cutover Planning

Zero-Downtime Cutover Strategy

  • T-1 day: Final validation, sync CDC data
  • T hour: Pause new writes to source system
  • T+5 min: Drain all pending CDC changes
  • T+10 min: Update application connection strings
  • T+15 min: Resume application traffic to ClickHouse
  • T+1 hour: Monitor for errors and performance
  • Maintain rollback: Keep source active for 24 hours
🎯 When to Use Which Migration Approach

Use Kafka + Debezium CDC When:

  • Data volume is massive (1TB+)
  • Cannot afford downtime
  • Continuous changes during migration
  • Need real-time analytics post-migration
  • Complex transformations needed

Use Simple Bulk Load When:

  • Data volume is small (< 100GB)
  • Can afford brief downtime
  • One-time migration
  • Simple schema mapping
  • No data changes during migration

Migration Decision Matrix

Scenario Recommended Approach Estimated Duration Risk Level
< 10GB, 1 table, no changes Direct bulk load 1-2 hours Low

Template 3: Data Validation Query

-- Comprehensive validation across source and target
WITH counts AS (
    SELECT
        'total_rows' as metric,
        COUNT(*) as count,
        0 as status
    FROM users
),
null_checks AS (
    SELECT
        'null_count_email' as metric,
        countIf(email IS NULL) as count,
        countIf(email IS NULL) as status
    FROM users
),
duplicates AS (
    SELECT
        'duplicate_ids' as metric,
        COUNT(*) as count,
        countIf(cnt > 1) as status
    FROM (
        SELECT id, COUNT(*) as cnt
        FROM users
        GROUP BY id
    )
)
SELECT metric, count, status FROM counts
UNION ALL
SELECT metric, count, status FROM null_checks
UNION ALL
SELECT metric, count, status FROM duplicates;
🔥 Advanced Migration Patterns

1. Gradual Read Migration Pattern

-- Instead of hard cutover, gradually route traffic to ClickHouse
-- Using application-level routing (pseudo-code)

if featureFlag("use_clickhouse_analytics", user_id) {
    // 5% of users read from ClickHouse
    result = query_clickhouse(sql)
} else {
    // 95% still using MongoDB
    result = query_mongodb(sql)
}

// In week 1: 5% → ClickHouse
// In week 2: 25% → ClickHouse
// In week 3: 75% → ClickHouse
// In week 4: 100% → ClickHouse

// This allows:
// - Detection of any ClickHouse-specific issues
// - A/B testing for performance
// - Quick rollback by adjusting flag

2. Schema Evolution with ReplacingMergeTree

-- Handle schema changes during migration
-- MongoDB adds new field:
db.users.updateMany({}, {$set: {new_field: ""}})

-- ClickHouse: Add column BEFORE data arrives
ALTER TABLE users ADD COLUMN new_field String DEFAULT '';

-- ReplacingMergeTree keeps latest version based on updated_at
CREATE TABLE users (
    id String,
    name String,
    email String,
    new_field String DEFAULT '',  -- New column
    updated_at DateTime,
    version UInt32 DEFAULT 1
) ENGINE = ReplacingMergeTree(version)
ORDER BY id;

-- Later, drop old column
ALTER TABLE users DROP COLUMN old_field;

-- Monitor schema changes
SELECT name, type
FROM system.columns
WHERE table = 'users'
ORDER BY name;

3. Handling Deletes with ReplacingMergeTree

-- When source deletes records, mark them as deleted in ClickHouse
-- Instead of physical deletion, use a flag

CREATE TABLE users (
    id String,
    name String,
    email String,
    is_deleted UInt8 DEFAULT 0,  -- Soft delete flag
    updated_at DateTime,
    version UInt32
) ENGINE = ReplacingMergeTree(version)
ORDER BY id;

-- In application, when reading:
SELECT * FROM users
WHERE is_deleted = 0  -- Exclude deleted
  AND id IN (...)

-- Periodically clean up old versions:
-- ClickHouse automatically merges ReplacingMergeTree
-- Keeping only latest version per key

-- Query to see deleted records:
SELECT * FROM users FINAL WHERE is_deleted = 1;

4. Monitoring Migration Progress

-- Check Kafka lag
kafka-consumer-groups --bootstrap-server kafka:9092 \
  --group clickhouse_users \
  --describe

-- Check ClickHouse insert rate
SELECT
    database,
    table,
    sum(bytes) as total_bytes,
    max(modification_time) as last_modified,
    formatReadableSize(total_bytes) as readable_size
FROM system.parts
WHERE table IN ('users', 'orders', 'products')
GROUP BY database, table
ORDER BY last_modified DESC;

-- Check query log to see if migration queries are happening
SELECT
    query,
    query_duration_ms,
    read_rows,
    read_bytes,
    written_rows,
    type
FROM system.query_log
WHERE table IN ('users', 'orders', 'products')
  AND event_date >= today()
ORDER BY event_time DESC
LIMIT 20;

-- Monitor Debezium lag
curl http://localhost:8083/connectors/mongo-connector/status | jq '.tasks[].payload'
